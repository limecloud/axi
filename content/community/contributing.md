# 贡献与演进

AXI 当前是草案。贡献应从可复现的任务问题出发，让规则、Schema、示例和验证一起变化。

## 小型修订

文字澄清、失效链接和不改变语义的示例修正可以直接提出变更。说明读者问题、修改位置及验证结果；正文只描述最终合同，历史写入[变更记录](changelog.md)。

## 规范提案

修改核心字段、状态、副作用、错误语义、扩展机制或符合性要求时，先给出提案。无需为拼写修正建立复杂流程。

```text
标题：解决的具体问题
状态：草案 / 待评审 / 接受 / 拒绝 / 撤回
动机：真实任务与失败证据
范围：修改的要求编号、Schema、绑定与采用方
设计：精确字段、状态、顺序与完整示例
替代方案：为何现有合同不够
兼容：旧客户端、缓存、原操作恢复与迁移
安全：身份、授权、注入、敏感数据与副作用
验证：正例、负例、互操作和目标任务
未解决问题：影响采用决定的缺口
```

提案状态不是当前规范状态。未接受内容不得作为必需行为加入教程或默认测试。

## 变更检查

1. 确认要求有唯一归属，导读只引用，不重复定义。
2. 调整版本与兼容说明，确保旧操作恢复不被破坏。
3. 同步 Schema、样例、方法、绑定和负例测试。
4. 严格构建并验证所有链接、图表、搜索、桌面和窄屏。
5. 在声明中区分参考实现、协议夹具和真实宿主任务。

本仓库的实际命令见仓库 `README.md`。不把外部基准的结果复制为 AXI 的性能承诺，不虚构兼容实现、认证机构或工作组。

## 评审关注点

规则是否有具体失败模式与可验证判据？增加的字段或调用是否帮助客户端作下一步决定？是否可用已有传输与业务用例实现？能否通过更窄的合同解决，而不增加任意执行器、第二套事实源或新的授权系统？

外部资料的采纳必须说明来源、日期和独立取舍。参考站点更新不会自动更改本规范。
