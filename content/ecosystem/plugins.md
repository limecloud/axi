# 插件与分发

插件把方法、工具连接与可选资源组织成可发现、可安装的产品。AXI 复用载体的原生包格式，不另造通用插件安装器。

## 两个不同的目录

**分发目录**回答“在哪里获得插件、来自谁、哪个版本、如何安装”。**能力目录**回答“已启用的提供方有哪些动作、输入与上下文”。前者不能证明连接和授权，后者不能代替软件供应链校验。

## OpenAI / Codex 插件

2026-11-08 核对的官方文档支持在包根使用 Agent Plugins `plugin.json`，可带 `skills/` 和 `mcp.json`。OpenAI 特定展示、注册服务映射等放在 `extensions.com.openai`；`.codex-plugin/plugin.json` 仍是受支持的兼容入口。它们是宿主包格式，不能混成 AXI 的网络消息。

```text
package/
├── plugin.json          # 载体原生清单
├── mcp.json             # 可选：原生 MCP 连接定义
└── skills/
    └── document-review/
        └── SKILL.md
```

原生清单的精确字段、Schema 版本与适用表面按官方文档冻结。迁移不能只把 `.mcp.json` 改名：格式和 transport 声明也可能不同。本文不提供未经当前宿主验证的“万能清单”。

## 安装来源与信任

仓库/个人 marketplace、工作区发布和公共目录是不同渠道，权限和安装策略可能不同。安装器应展示发行者、精确版本、来源及所需执行/连接能力；不能把“来自 GitHub”当作可信证明。

本地可执行组件需要额外说明运行平台、依赖、启动/停止、端口与升级。生命周期 hooks 受宿主和安装模式约束，不能假设所有插件都支持；不应为普通方法引入自动执行 hooks。

## 包与远程服务独立更新

远程 MCP 服务可以在包不变时更新。能力目录和 Schema 因而应以实际服务为准，并保证合同修订与缓存失效。包审核通过不意味着所有未来服务变化都已获准。

发布与更新分别验证包、连接、身份、工具、方法、UI 和真实任务。公共发布涉及平台审核，审核通过、点击发布和用户实际可安装仍需分开核对，见[发布流程](../lifecycle/release.md)。
